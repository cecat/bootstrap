## The one thing to get right

**The deliverable is the repo, not the VM.**

This project exists so that *another* coding agent can clone it, stand up Pi
inside a VM, and have **Pi** build the two agents from `spec/pi-target-state.md`.
Teaching Pi to fish. The VM on this machine is a test fixture — its only
purpose is to tell us whether the writing works.

That has a hard consequence:

> **When something breaks, fix the script or the spec, then rerun. Never
> reach into the VM to fix it by hand.**

A VM made to work by hand is worse than a broken one, because it looks like
success while the repo still produces failure for the next person. This rule
was broken twice on 2026-10-26 and both times destroyed the evidence.

The corollary: the only measure of progress is **does Pi, reading only the
committed spec, produce a working result unaided?** Nothing typed into the
VM counts.

### What just happened (item 1 of a four-step plan)

`spec/pi-target-state.md` was actively preventing Pi from setting up Hermes'
Telegram channel. It said *"No systemd service, and this is correct… Do not
install it"*, conflating **installing the machinery** with **enabling the
channel**. Four specific corrections are now committed (`63a2897`):

1. `hermes gateway install` is required when Telegram tokens are present.
2. `telegram-platform` ships **installed but disabled** — needs
   `hermes plugins enable telegram-platform`, or the journal says
   `No adapter available for telegram` while the service sits active.
3. Its `python-telegram-bot` dependency is fetched from **pypi.org**, which
   is allowlisted in **bootstrap only**. First start must therefore happen
   during the Pi phase.
4. The claim *"there is no non-interactive `hermes setup`"* was false;
   `hermes setup --non-interactive` and `hermes setup gateway` both exist.

`verify.sh` now keys the Hermes gateway check on `TELEGRAM_BOT_TOKEN` in
`~/.hermes/.env` (it had keyed on `channel_directory.json`, a file Hermes
never writes, so it passed unconditionally) and separately asserts the
adapter connected.

**None of this is proven.** It was established by hand, and the current VM is
contaminated by exactly those manual fixes.

## What to do next — steps 2, 3, 4

### 2. Write `bootstrap.sh`, shrink `AGENTS.md`

This is the real fix and it comes before any more rebuilds. See `todo.md`
item 3, which has argued for it since before this session.

Steps 0–9 of `AGENTS.md` are deterministic: detect model access, start the
VM, generate config, push it, hand the spec to Pi, narrow egress, verify.
Driving them with a coding agent adds variance without adding judgment —
and every contaminating hand-fix this session happened because an agent was
driving those steps and could reach past them. A script cannot improvise.

Two things stay interactive, because a script genuinely cannot do them:
confirming the detected model access, and the user editing
`config/agents.env` with their own bot tokens (never ask for a secret in
conversation — that rule is not negotiable).

`AGENTS.md` then collapses to roughly: *run `./bootstrap.sh`; it will stop
and ask you for agent names and tokens; do not reach into the VM.* Pi stays
inside, where the work is genuinely open-ended: installing third-party tools
whose docs drift, and writing the idempotent `setup.sh`.

### 3. Rebuild from nothing

```sh
limactl delete -f agents
rm -f config/allowlist-*.conf config/model-access.env \
      config/model-gateway config/pi-models.json config/agents.env
```

Keep `local/` (gitignored; see below). Then run the new `bootstrap.sh`.

Delete `config/agents.env` too, and re-enter the tokens. Pre-populating it
gives Pi an artificially easier task and risks a false pass — the user made
this call explicitly and it was the right one.

### 4. Add any missing verify checks

`verify.sh` grew several checks this session, each because something passed
while being wrong. Keep that habit: when a defect is found, the fix is a
check that fails on it, not just prose in the spec.

## Hard-won facts worth not rediscovering

**On this host:** use `sg kvm -c '...'` for every `limactl` command. A
`setfacl` grant on `/dev/kvm` does not survive the udev event that
installing qemu triggers; group membership does. Also, NextDNS blocks the
NVIDIA apt repos, which looks alarming during `apt-get update` and is
irrelevant to this build.

**`VM_BASE_URL`, never `UPSTREAM_BASE_URL`.** The latter is the *host's*
address, often `127.0.0.1:<port>`, which from inside the VM is nothing.

**A systemd user service does not read `~/.profile`.** Without a proxy
drop-in the gateway reaches the model fine (direct, uid-allowed) and fails
every allowlisted destination with `EHOSTUNREACH`. That combination passes
`--models` 30/30 and cannot reach a single chat channel.

**`/health` and `/v1/models` are false greens.** Only a completion proves
the model path.

**Guards that grep multi-line JSON never match.** `grep -q
'"botToken".*"source":"env"'` against pretty-printed JSON silently makes its
step unconditional. Use `jq -e`.

**`openclaw onboard` names the agent `main`** and ignores
`OPENCLAW_AGENT_NAME`. The id is immutable; `set-identity` sets the display
identity. `Agent dir:` in `openclaw agents list` carries a trailing
`/agent`, and prints a literal `~` that no shell expands.

**SOUL.md guards must check content, not existence.** The Hermes installer
writes its own vendor persona, so `[ -f ] && skip` leaves an agent that has
never heard of the configured name.

## Where the user's files are

`local/` is gitignored and holds `local/souls/` — hand-written `SOUL.md`
content migrated from another deployment. Installing those is a **one-time
manual exception** the user has approved, and is explicitly *not* something
the repo should automate (`AGENTS.md`: the repo ships a seed, never a
managed file). Do not build a sync mechanism for them.

Both files were edited to include an explicit `You are <NAME>` line, because
the content-based SOUL guard needs it and would otherwise overwrite them.

## A pattern to watch in yourself

Three times this session a `verify.sh` check was wrong and Pi was right:
asserting a gateway method that OpenClaw had removed, requiring a service
that correctly did not exist, and demanding an agent directory name the tool
cannot produce. Each came from writing a check against what output *looks
like* rather than what the system *does*.

Check the tool's actual model before writing the assertion. And when Pi
reports something surprising, verify it before assuming Pi is wrong.
